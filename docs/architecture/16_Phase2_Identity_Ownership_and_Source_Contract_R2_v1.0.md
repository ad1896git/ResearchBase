On acceptance, it supersedes the PR2-00/01 portions of correction 12 §3/§7.1, field contract 13 §§Organization and identity/Literature identity, and the rejected PR2-01 v1.0 pack where they conflict. It does not edit those historical design files or authorize PR2-02. ## Boundary and principal model

An ActorIdentity is a stable attribution identity, not proof of control of its `external_key`. Phase 1 actor/project rows and historical `created_by` values are never rewritten. An authenticated principal is derived by a deployment adapter and bound to an actor through `actor_subject_bindings` (0019). The Application receives a typed `VerifiedPrincipal` containing deployment ID, subject kind, normalized subject, proof/credential ID, and verification time from a trusted adapter; request body, `X-Actor-ID`, display name, and Agent assertion cannot construct it. An optional `X-Actor-ID` must equal the resolved actor. A missing/ambiguous/revoked binding fails closed. Actor retirement fails closed.

The DEV_LOCAL OS adapter obtains numeric UID from the kernel (`getuid`/peer credentials), not a flag; it checks deployment allowlist and maps `(deployment_id, OS_UID, decimal UID)`. The HTTP adapter verifies a client certificate against the configured CA, checks validity/revocation and URI SAN, then maps `(deployment_id, MTLS_URI, exact URI)`. It must not trust proxy headers without a separately reviewed trusted ingress contract. Proof/credential identifiers and SHA-256 evidence digests are audit metadata; secret bytes, private keys, and certificates are not canonical data. TEAM/HPC may use a reviewed equivalent adapter with explicit subject type and issuer. No adapter means HTTP Phase 2 writes fail 401.

Three ceremonies are distinct:

1. **First bootstrap:** only if both `actors` and `projects` are empty. A host operator in the deployment allowlist presents the one-use secret file (0600, outside repository), verified OS UID, and configured DB credential. The CLI verifies the configured secret digest and passes `BootstrapAuthority` to `bootstrap_first_owner`. A signed, secret-free operator proof record is retained in the deployment audit store before the transaction. One SERIALIZABLE transaction plus transaction advisory lock inserts the first HUMAN actor with `external_key=local-os:<deployment_id>:<uid>`, its OS subject binding, first Project, ACTIVE membership, OWNER role, and immutable BootstrapRecord. The `request_fingerprint` is `sha256-cjson-v1` of exactly `{"type":"BOOTSTRAP_FIRST_OWNER","material_version":1,"deployment_id":"<string>","operator_credential_id":"<string>","verified_os_uid":0,"display_name":"<string>","project_name":"<string>"}` with UID as nonnegative JSON integer and names NFC-normalized, outer-trimmed, nonblank strings; the secret and request UUID are excluded. Every later bootstrap invocation, including the same request UUID and input, is rejected `BOOTSTRAP_CLOSED`; the immutable record is available only through an authenticated operator audit query. The one-use secret is invalidated on successful commit and never authorizes a second write. There is no HTTP bootstrap route.
2. **Legacy subject binding:** applies to an existing HUMAN actor with `external_key IS NULL` and no active subject binding. A live subject proves its OS account or mTLS key to the adapter, and an independent deployment operator verifies contemporary identity evidence linking that subject to the named actor. The operator must create a signed onboarding attestation that explicitly names the existing actor UUID, deployment ID, subject kind/value, operator credential ID, subject credential ID, fresh challenge nonce/digest, proof method, evidence source and UTC time. The live subject must answer that challenge through the verified OS peer session or mTLS private-key handshake; the operator and subject cannot be the same principal. Store the secret-free signed attestation in a deployment-controlled immutable, content-addressed audit file before commit and persist its digest/reference. Missing signature, unavailable audit file, expired challenge or absent evidence tying this actor UUID to the subject fails closed. `bind_legacy_actor_subject` under a deployment lock checks actor type, subject uniqueness and non-retirement, inserts an append-only binding and event, and never updates the actor or old attribution. Name, `projects.created_by`, old request headers and historical logs alone are insufficient proof. If the evidence cannot establish the link, bind is refused and a new actor is provisioned. Binding is effective only from `bound_at`; queries label earlier historical actions as legacy attribution, not authenticated proof. Revocation closes the binding and appends an event; it does not erase history.
3. **Post-bootstrap actor provisioning:** `provision_actor` requires an authenticated current HUMAN OWNER of at least one active project, a fresh live proof from the proposed subject, and an independent allowlisted operator attestation. It stores the signed onboarding record described above and creates a new HUMAN actor and binding atomically, with no project role granted by default. Service/Agent provisioning is a separate reviewed adapter policy and cannot use human proof. A retired actor or duplicate subject cannot be provisioned. The Phase 1 internal `create_actor` stays available for Phase 1 compatibility but conveys no Phase 2 authentication until a binding ceremony succeeds.

Each successful ceremony writes an immutable `actor_subject_binding_events` row with command/request ID, actor, operator credential ID, proof kind, signed proof digest/reference and timestamp. The audit file is a protected deployment artifact, not ResearchBase canonical scientific state; its content hash and retained bytes are inspectable by an operator. `subject_credential_id` is the OS credential reference or mTLS certificate fingerprint, never a caller-supplied name. For failed validation, record a redacted operational security log outside the rolled-back canonical transaction; do not create a misleading success row. No successful canonical binding can exist without its event. BootstrapRecord continues to own the first-owner audit fact; binding events own authentication link facts. A first-owner subject binding is linked to BootstrapRecord in that same transaction. Read access to proof metadata is operator-limited.

## Project membership and continuous OWNER coverage

A membership is ACTIVE/SUSPENDED/ENDED. An assignment has a half-open interval `[effective_from,effective_until)`; null upper bound means unbounded. At DB time `t`, an effective OWNER requires an ACTIVE membership, an OWNER assignment covering `t`, and a non-retired actor with an active authenticated binding. A project admitted to Phase 2 has continuous OWNER coverage from `ownership_started_at` (the immutable FIRST_BOOTSTRAP or PROJECT_ENROLLMENT membership-event timestamp) forward: the union of effective OWNER intervals, intersected with membership ACTIVE intervals, must contain every instant from start through now and have at least one open-ended future coverage path. Merely having a finite OWNER interval that covers the current instant is insufficient. A future gap, last OWNER role expiry, suspension/ending, retirement, or binding revocation is rejected unless a replacement OWNER becomes effective no later than the lost coverage in the same transaction. For planned finite intervals, the transaction must supply successor intervals that touch or overlap without gaps and end in an open interval. No backdating a role to conceal a prior gap. Clock comparison uses DB time and serialized per-project ownership lock.

`create_project_with_owner` creates Project, membership, open-ended OWNER assignment and immutable enrollment event in one transaction. `enroll_legacy_project_owner` requires the actor equal to immutable `projects.created_by`, an active secure subject binding, and operator attestation; it starts coverage at enrollment DB time and explicitly marks earlier project history as pre-enrollment. It never fabricates earlier OWNER history. Phase 2 commands deny access until enrollment. Reactivation from SUSPENDED/ENDED creates a **new** membership row and a new OWNER assignment if needed; it cannot reopen or change the prior interval. Suspension/ending and role close append events, preserve old rows, and run the coverage guard. Project archive does not delete records. Phase 1 `create_project` and data remain unchanged.

Database enforcement uses one project-scoped transaction advisory lock for all role/membership/binding changes affecting OWNER coverage, SERIALIZABLE isolation, an exclusion constraint preventing overlapping same membership/role intervals, interval CHECKs, active-membership uniqueness, and a deferred constraint trigger that verifies continuous coverage at commit for enrolled projects. ACTIVE membership history is reconstructed from immutable events: the initial ACTIVE interval ends at the SUSPENDED or ENDED event, and a suspended row never becomes ACTIVE again. A small guard trigger on existing `actors.retired_at` blocks retirement that would remove the last effective OWNER; this adds no Phase 1 column or historical rewrite and is an explicit R2 deviation from the earlier 0019 no-Phase-1-table-trigger wording. Application checks produce named errors; DB trigger protects direct/concurrent writes. Actor binding revocation and retirement acquire locks for every affected enrolled project in stable UUID order. An attempted raw SQL close that would orphan a project must fail. A scheduled finite expiry cannot silently leave a gap: all admitted project OWNER coverage has an open-ended successor at commit.

## Source identity and normalization (`source-identifier-normalization-v1`)

`LiteratureSource` is a global public identity; `literature_source_project_links` grant scoped access. Source title is registration display text, NFC/trimmed and immutable; it is not identity proof or formal content. PR2-01 status is ACTIVE/RETIRED; MERGED/aliases/SourceMergeRecord and SourceVersion arrive only in PR2-02. Every create/lookup requires an explicitly supplied project, active membership and link, except a registration may atomically add a link to an existing global source. An unauthorized or unlinked lookup returns the same not-found shape as an absent source. It never reveals other project associations. OWNER/RESEARCHER may write; VIEWER/REVIEWER/APPROVER may read under an active membership. Agents obey identical Application policy after authenticated binding.

Input is Unicode NFC and trimmed at both ends; reject controls, surrogates, empty values, encoded control characters and normalized strings over 2048 code points. Percent decoding is exactly once where stated; malformed UTF-8/percent encoding is rejected. All wrappers must be exact recognized host/scheme/path forms, with no credentials, query or fragment unless allowed below.

| Type | Exact normalized form and rejection |
|---|---|
| DOI | Accept bare `10.<4-9 ASCII digits>/<nonempty suffix>`, `doi:` prefix, or `https://doi.org/` / `http://dx.doi.org/` wrapper. Decode only RFC 3986 unreserved percent bytes once; reject encoded slash/control and malformed escapes. ASCII-lowercase the DOI; preserve suffix punctuation and non-ASCII NFC. No URL query/fragment. |
| ARXIV | Accept bare, `arXiv:`, or `https://arxiv.org/abs/` or `/pdf/` wrapper (terminal `.pdf` only for `/pdf/`). Modern ID: four ASCII year/month digits, dot, 4 or 5 digits, valid month 01–12. Legacy ID: ASCII archive `letters` with optional `-letters`, slash and 7 digits. Optional `v[1-9][0-9]*` is removed from work identity and returned as noncanonical version hint. Archive lowercase; reject other wrapper paths, queries/fragments and malformed version tails. |
| PMID | ASCII digits only, positive; remove leading zeros. |
| ISBN | Remove ASCII spaces/hyphens, uppercase X only in ISBN-10 final position; validate ISBN-10/13 checksum. |
| URL | Absolute HTTP/HTTPS only. RFC 3986 parser with UTS #46 nontransitional processing, STD3 rules, NFC and IDNA2008 validation for each DNS label; output lower-case A-label hostname. Reject invalid IDNA, credentials, empty host, IP zone ID, backslash, controls and non-default invalid port. Lowercase scheme/host, remove default :80/:443, omit fragment, use `/` for empty path, preserve path and query ordering/case, decode only unreserved percent bytes once and uppercase hex in retained escapes. Dot-segment removal follows RFC 3986; do not collapse repeated slashes. IP literals use canonical RFC 5952 IPv6 or normalized IPv4. |
| SEMANTIC_SCHOLAR | Exactly 40 ASCII hexadecimal characters, lower-case. No wrapper. |
| OPENALEX | `W` plus positive ASCII decimal integer, optional exact `https://openalex.org/` wrapper; output uppercase W and canonical integer. |
| OTHER | `namespace:value`; namespace lower-case ASCII `[a-z0-9][a-z0-9._-]{1,63}`, registered by deployment before use; nonempty NFC value preserves case. Unknown namespace rejected. |

The Application computes normalization before persistence and stores both input and normalized text. PostgreSQL uniqueness covers all UNVERIFIED/VERIFIED rows by `(identifier_type, normalized_value)`. Identical title, provider score, different DOI or unverified collision never auto-merges identities. A verified duplicate may return the existing source only if source kind and NFC/outer-trim title exactly equal the registered values and authorized project link is atomically added; otherwise `SOURCE_IDENTITY_CONFLICT`. Primary designation is unique among non-rejected identifiers for one source. A REJECTED row remains immutable historical evidence and permits a new binding of the same normalized value. See rejection and idempotency below.

## Identifier verification, rejection and rebinding

`SourceIdentifier` identity fields (source, type, raw/normalized value, primary designation) never change. Status is UNVERIFIED→VERIFIED/REJECTED or VERIFIED→REJECTED; REJECTED is terminal. Verification is a typed Application command requiring active OWNER/RESEARCHER, a FROZEN identity-basis ArtifactVersion, a reason, and an append-only `SourceIdentifierVerificationEvent` in the same transaction. Rejection additionally requires an authenticated HUMAN OWNER of the identifier source's sole linked project; if two or more project links exist, it fails `SHARED_SOURCE_REJECTION_REQUIRES_REVIEW` without mutation. Cross-project binding correction is deferred to PR2-02 with independent authority design. The event records prior/new state, actor, basis FK, reason, occurred_at and command request ID. Verification fields are present iff VERIFIED. On rejection, `verified_at/by/basis` are cleared as current-state fields, while the verification event preserves original proof; the rejection event and basis explain why. The rejected row cannot be revived, edited, deleted or silently moved to another source.

`reject_source_identifier` is exposed by HTTP `POST /v1/projects/{project_id}/literature/identifiers/{id}:reject` and CLI `researchbase literature identifier reject --project-id --identifier-id --basis-artifact-version-id --reason --request-id`; both pass the same typed command and authenticated actor. The operation is permitted on UNVERIFIED or VERIFIED only. If the identifier was primary, the source has no primary after rejection; another existing row is never silently promoted. A new primary may be added through a later `add_source_identifier` command. Rebinding is a **new** `add_source_identifier` row with an independently frozen basis and explicit target source after the prior row is REJECTED; never an UPDATE to old row. The new row starts UNVERIFIED, remains unique among live bindings, and must be verified separately. Concurrent reject/rebind serializes on `(identifier_type,normalized_value)` advisory lock and the partial unique index. Rejection and new project link insertion also lock the source ID before the sole-link check, preventing a shared-source race. Lookup never treats rejected history as an active binding.

## Durable PR2-01 command idempotency

`register_literature_source`, `add_source_identifier`, `verify_source_identifier`, and `reject_source_identifier` each require caller `request_id UUID` (HTTP `Idempotency-Key`, CLI `--request-id`; missing/invalid identifier is `VALIDATION_ERROR`, 422, before mutation). The key scope is `(deployment_id, project_id, authenticated_actor_id, command_name, request_id)`. A row in `literature_command_receipts` is persisted in the same transaction as the canonical result and contains that exact scope, `input_hash CHAR(64)`, `hash_scheme=sha256-cjson-v1`, `result_source_id UUID`, nullable `result_identifier_id UUID`, nullable `result_verification_event_id UUID`, `result_dto_version SMALLINT`, `result_dto JSONB` containing only a versioned public response projection, and `completed_at TIMESTAMPTZ`. `result_dto` is a replay cache, not canonical science. Input hash is `sha256-cjson-v1` over the literal command payloads below, excluding request ID and transport headers; authenticated actor/project/deployment are in the receipt scope. The optional initial identifier is serialized as null when absent, never omitted.

```text
REGISTER_LITERATURE_SOURCE: {"type":"REGISTER_LITERATURE_SOURCE","material_version":1,"kind":K,"title":NFC_TRIM_TITLE,"initial_identifier":null|{"identifier_type":T,"normalized_value":V,"normalization_version":"source-identifier-normalization-v1"}}
ADD_SOURCE_IDENTIFIER: {"type":"ADD_SOURCE_IDENTIFIER","material_version":1,"source_id":UUID,"identifier_type":T,"normalized_value":V,"normalization_version":"source-identifier-normalization-v1","is_primary":BOOL}
VERIFY_SOURCE_IDENTIFIER: {"type":"VERIFY_SOURCE_IDENTIFIER","material_version":1,"identifier_id":UUID,"basis_artifact_version_id":UUID,"reason":NFC_TRIM_REASON}
REJECT_SOURCE_IDENTIFIER: {"type":"REJECT_SOURCE_IDENTIFIER","material_version":1,"identifier_id":UUID,"basis_artifact_version_id":UUID,"reason":NFC_TRIM_REASON}
```

UUID values are lowercase canonical strings, enum values uppercase, and normalized values are produced by the versioned algorithm. Raw identifier spelling is excluded intentionally because equivalent input has the same semantic command; the stored raw spelling and replay DTO come from the first successful request. `register` returns source ID and optional initial identifier ID; `add` returns source/identifier IDs; `verify` and `reject` return source/identifier/event IDs. Each receipt has concrete FK to each nonnull result and a command-specific CHECK for required/null result fields.

The Application acquires a transaction-scoped advisory lock on the receipt scope, checks for a committed receipt, performs the command when absent, and inserts a complete receipt with the result in the same transaction. The unique scope remains the database backstop. Same scope+hash returns stored DTO/IDs after rechecking current access; same scope+different hash raises `IDEMPOTENCY_CONFLICT` 409 with no mutation. A replay after role revocation fails authorization; receipts do not grant access. Concurrent same-key requests serialize on the unique key and yield one canonical result. If a transaction rolls back, no receipt or canonical row survives, so retry can execute. Different keys remain subject to identifier uniqueness and identity conflicts; no random duplicate creation is accepted as idempotency. Receipts are immutable after completion, never store secrets, and are retained for the lifetime of related source identity. A compatibility/version bump may project the saved result IDs into a new DTO only under an explicit compatibility rule; never recalculate a different canonical result.

## Acceptance and STOP

PostgreSQL 18.x tests must prove all stated constraints, serializable races, legacy signed proof refusal/success, new actor provisioning, bootstrap replay, zero OWNER gaps including finite expiry and reactivation, cross-project isolation, normalization vectors, sole-project rejection/shared-source refusal/rebinding, and durable four-command replay/conflict/rollback. API and CLI parity and exact audit event FKs are required. Migration 0019 is accepted before 0020. No Phase 1 row/hash is rewritten. No PR2-02 SourceVersion, merge, alias, provider call or governance implementation appears in these PRs. Any P0/P1 finding, missing required test, migration scope drift or architecture conflict stops the respective PR gate. Design acceptance is not implementation permission.
