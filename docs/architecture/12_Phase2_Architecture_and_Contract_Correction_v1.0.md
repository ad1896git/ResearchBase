# Phase 2 Architecture and Contract Correction v1.0

**Status:** normative design correction for Phase 2 reauthorization review. This document does not authorize implementation.  
**Precedence:** incorporated by Final Architecture Correction Addendum A17; clarifies the System Architecture's Phase 2 submission placement and patches the Phase 2 specification's conflicting package wording. The Global Registry is updated with the decisions below. Phase 1 semantics and `phase1-final-v4` are untouched.  
**Scope:** the seven entry-gate gaps, literature scope, conclusion and publication boundaries. New canonical objects in this correction are approved *design names* only. Any implementation still requires the separate PR gate.

## 1. Phase boundary and publication correction

`LITERATURE_IN_PHASE2 = YES`. Literature source/version, search, evidence, the native STORM-like strategy and bounded PaperQA2 adapter are Phase 2 work. Full Agent Runtime, Planner/Executor/Reviewer orchestration, background automation, UI/desktop, venue connectors and Phase 3/4 objects are excluded. The entry-gate checklist's reference to excluding literature is corrected by this section; it did not reflect the System Architecture, Cross-Phase Contract or Phase 2 specification.

The phrase “SubmissionVersion is what was actually sent” in System Architecture §13 remains the definition of **SubmissionVersion**, but that object is deferred to the optional venue-submission extension. The Phase 2 prepared package is renamed **PreparedSubmissionVersion**. The Phase 2 spec §23 and PR2-17 references to `SubmissionVersion` mean `PreparedSubmissionVersion` only; the Global Registry and Cross-Phase §28 must be read accordingly. This is a deliberate higher-authority correction, not a reinterpretation by an implementation plan.

| Fact | Canonical owner | State and effect |
|---|---|---|
| ClaimVersion | research | One scientific assertion with exact evidence; Phase 1 frozen semantics unchanged. |
| ScientificConclusionVersion | research | Synthesis over exact frozen claims and/or verified literature evidence; no manuscript wording ownership. |
| ManuscriptVersion | publication | Exact manuscript wording/artifact and placements; presentation cannot create scientific support. |
| Publication | publication | Long-lived publication effort and current-manuscript navigation pointer. |
| PreparedSubmissionVersion | publication | Frozen package *intended* for possible submission; no claim that external delivery occurred. |
| ApprovalGrant | governance | Internal authority to perform a narrowly scoped future command; neither external effect nor delivery evidence. |
| SubmissionVersion | publication, deferred | Exact package actually sent, linked to a frozen PreparedSubmissionVersion and immutable external submission event. It cannot exist before a governed external send. |
| SubmissionRecord | publication, deferred | Append-only external attempt, provider/venue, request key, response and reconciliation status; may be UNKNOWN/FAILED/SUCCEEDED. A successful reconciled record creates or links SubmissionVersion. |

`ExternalEffect` remains the governed effect record in the later connector extension. A venue response cannot alter Claim, Conclusion, Manuscript or prepared package material. External statuses append records; they do not rewrite a historical send.

## 3. Actor bootstrap and project ownership

**Classification:** Phase 2 prerequisite deployment/bootstrap ceremony; it is not a retroactive Phase 1 semantic rewrite. Phase 1's existing Application `create_actor` is a valid internal operation but its public provisioning ceremony was unspecified. This correction defines a Phase 2 bootstrap contract and requires separate PR2-00 implementation before PR2-01. It does not change the frozen Phase 1 baseline.

Only a deployment operator whose OS user ID appears in the deployment bootstrap allowlist, with local host access, the configured database deployment credential, and a one-use bootstrap secret file may invoke `researchbase bootstrap first-owner` from the host CLI. The CLI obtains the OS user ID from the kernel, never a caller-supplied flag; the first HUMAN ActorIdentity has `external_key = local-os:<deployment_id>:<verified_uid>`, so later local authentication maps the same OS principal to that ActorIdentity. The actor display name is command input but does not establish identity. The file must be mode 0600 and outside the repository; its bytes never enter a log, canonical row or artifact. No HTTP bootstrap endpoint is permitted. The CLI validates the secret's deployment-configured SHA-256 digest and passes an authenticated `BootstrapAuthority` carrying verified deployment/UID/credential identifiers to a dedicated **Application** bootstrap command. Both Human and Agent continue to use the same ordinary Application commands after bootstrap; the narrowly scoped bootstrap command is unavailable to agents and regular API callers.

In one serializable PostgreSQL transaction under a transaction-scoped advisory lock, the command requires `actors` and `projects` both empty, inserts the first HUMAN ActorIdentity, first Project, ACTIVE ProjectMembership and OWNER ProjectRoleAssignment, and inserts an immutable BootstrapRecord. Its `created_by` and attribution fields bind the new actor; BootstrapRecord additionally holds the operator credential identifier (not secret), deployment ID, one-use request UUID, secret digest identifier, timestamp, new IDs and outcome. A reused request UUID with byte-identical normalized input returns the original IDs; any other reuse conflicts. A concurrent or later bootstrap, malformed secret, partial insert, or failed role assignment aborts atomically. Once actor count is nonzero, bootstrap is permanently closed; no fallback path silently creates an owner. The one-use secret is destroyed by deployment procedure after success.

`bootstrap_records` is an organization/identity boundary audit table with UUID PK, unique request UUID and deployment ID, actor/project/member/role concrete FKs, immutable material hash, and no delete cascade. A second operator can verify the record through an authorized read query. New **Phase 2** project creation uses `create_project_with_owner` and inserts an ACTIVE membership plus OWNER role in the same Application transaction. The frozen Phase 1 `create_project` command remains unchanged. A project created through that legacy path can be enrolled by a separate authenticated Phase 2 `enroll_project_owner` command whose actor must equal immutable `projects.created_by`; enrollment atomically creates the initial membership/OWNER and immutable enrollment event. Phase 2 commands reject a project until enrollment. This is an additive Phase 2 access contract, not a rewrite of Phase 1 project semantics. The external authentication adapter must establish actor identity; `X-Actor-ID` alone is attribution metadata and never sufficient authorization for Phase 2 governance.

For the DEV_LOCAL reference profile, CLI authentication uses verified OS UID and the `local-os:<deployment_id>:<uid>` ActorIdentity mapping. Phase 2 HTTP writes require an mTLS ingress adapter that verifies a client certificate against the deployment CA and maps a URI SAN of `urn:researchbase:actor:<external_key>` to the matching ActorIdentity; the deployment operator may receive such a certificate only through the separate certificate-issuance ceremony. A caller-supplied `X-Actor-ID` must match the resolved actor or the request fails 403. TEAM_SINGLE_NODE/HPC_RESEARCH may replace mTLS with a reviewed trusted identity adapter that maps an authenticated external subject to `ActorIdentity.external_key`; without a configured adapter, Phase 2 HTTP writes fail closed with 401. No bare bearer token, proxy header or agent assertion is trusted. Authentication implementations are adapters, not canonical scientific state. Integration acceptance uses a fake verified-principal adapter to test both Human and Agent calls against the same Application policy.

Acceptance: fresh DB succeeds once; concurrent attempts yield exactly one owner; replay of identical request is idempotent; changed replay and second bootstrap fail closed; bad secret leaves actor, project, membership, role and bootstrap tables empty; first project always has exactly one initial OWNER; no API route exposes bootstrap; audit record and actor/project attribution agree; Phase 2 project creation and legacy-project enrollment yield one initial OWNER without changing Phase 1 commands; Human/Agent ordinary commands share Application policies.

## 4. Hash and canonical material registry

All Phase 2 canonical hashes use `canonical-json-v1` UTF-8 bytes and `sha256-cjson-v1` unless a future ADR introduces a versioned new scheme. Persist `hash_scheme = sha256-cjson-v1` beside each own-content hash and binding hash. Hash payloads are JSON objects with the fixed `type` and `material_version = 1` discriminator. Field names below are literal; no implicit ORM fields enter. UUIDs are lowercase canonical strings; datetimes are UTC RFC3339 with six fractional digits and `Z`; dates are `YYYY-MM-DD`; enums are persisted uppercase names. Text is NFC-normalized without trimming except where a field explicitly says normalized; decimals use canonical decimal strings. Missing optional fields are serialized as `null`, never omitted. Object keys follow `canonical-json-v1`; array order is specified below. Stored `FrozenJSON` values are thawed only for canonical serialization.

Across all rows, exclude database ID, parent ID **unless listed**, version number **unless listed**, created/updated/frozen timestamps, actor attribution **unless listed**, row version, status, current pointer, hash fields themselves, and operational provider/cache metadata. This exclusion does not remove FKs from provenance: binding hashes and database constraints verify references separately. For an own-content hash, include exactly the fields in its row. `ref(T,id,hash)` is `{"type":T,"id":lowercase_uuid,"content_hash":lowercase_hex}` and must be verified against an immutable referenced record or frozen-material version. Frozen-material version means immutable with `frozen_at` and status FROZEN or SUPERSEDED; supersession never invalidates an exact historical hash by itself. `idref(T,id)` is `{"type":T,"id":lowercase_uuid}` for identity/actor/project rows without content hashes. A binding hash uses the listed sorted set or ordered list and the same discriminator convention. Duplicate set entries are rejected before hashing. Every freeze verifies referenced frozen/immutable material and current validity, recomputes bindings and own hash within its transaction, then seals material. Every read used for formal provenance recomputes and compares hashes and returns `HASH_MISMATCH`/`PROVENANCE_CLOSURE_VIOLATION`, never a silent warning. Ordinary history reads may show an invalidity marker without treating it as valid evidence.

## 5. ScientificConclusion closure

`ScientificConclusion` is an identity root scoped to Project, with `current_version_id` referencing one of its own versions. Its Version is a synthesis, never a Claim alias or manuscript paragraph. `scope` is schema-validated JSON with exactly `population`, `conditions`, `time_window`, and `applicability`, each a nonblank string or null; it contains no canonical IDs. `statement` is nonblank and `confidence` is STRONG/MODERATE/WEAK/INCONCLUSIVE/MIXED. DRAFT may add/remove typed ClaimVersion and LiteratureEvidence inputs. Each input row has immutable exact target ID, relation type (`SUPPORTS`, `CONTRADICTS`, `QUALIFIES`), and unique ordinal. At freeze: at least one input; every ClaimVersion has frozen material with valid Phase 1 closure and current validity; every LiteratureEvidence content hash valid, verification state VERIFIED for a material support assertion, and its SourceVersion frozen-material and non-retracted at that time; recompute support-set and content hashes; seal input rows. A contradiction may be recorded but cannot be silently counted as support. INCONCLUSIVE/MIXED are valid conclusions with accurately typed support and limitations.

Supersession creates a new DRAFT Version under the same identity and only switches the same-parent current pointer after its freeze; old FROZEN rows and input sets remain. Later retraction, corrected source, invalid Claim or AuditFinding marks current validity STALE/INVALID through a derived assessment/query; no old conclusion bytes or hash change. Downstream ManuscriptVersion placements hold exact frozen conclusion version IDs; current pointer lookup is never historical evidence. A new manuscript version is required to change a placement.

## 6. Governance authority and transitions

Roles are contextual ProjectRoleAssignments, never actor subclasses. OWNER can administer membership and assign roles; RESEARCHER may draft; REVIEWER may review; APPROVER may approve; VIEWER reads. No actor may review or approve their own target or a target they materially authored. OWNER does not bypass scientific or conflict checks. Membership must be ACTIVE, role assignment effective at command time, and project not ARCHIVED. A role can be held by a Human or Agent actor, but ApprovalDecision requires a HUMAN APPROVER; Agent suggestions remain candidates.

Every ACTIVE Project enrolled in Phase 2 must retain at least one ACTIVE OWNER assignment. Ending/suspending the last OWNER or archiving the sole owner membership fails in the same transaction; ownership transfer inserts the successor assignment before closing the predecessor. The database enforces this with a deferred constraint trigger, and Application checks provide the named error `LAST_PROJECT_OWNER`.

| Transition/command | Role | Target and deterministic checks | Review/decision/grant | Failure/audit |
|---|---|---|---|---|
| Create/revise draft conclusion or manuscript | RESEARCHER or OWNER | Project active; exact referenced identities exist | None | Conflict/404; actor, input refs and command correlation recorded. |
| Freeze conclusion | RESEARCHER or OWNER | DRAFT, valid frozen input closure and hashes | No review or grant required | Fail `PROVENANCE_CLOSURE_VIOLATION`; record actor/time and digest. |

Grant scope is a typed projection `(project_id, purpose, concrete target FK from ApprovalRequest, target_content_hash, allowed_command, max_uses=1, valid_until)`. It is never wildcard and is never persisted as generic `target_kind + target_id`. Phase 2 `APPROVE_WITH_CONDITIONS` permits only `valid_until` and `requires_current_author_consent`; both are typed decision columns and are rechecked at consumption. Unrecognized/free-text executable conditions are rejected. Consumption is atomic with the authorized transition, protected by row lock and unique consumption row; retry with same command key returns prior result, different retry fails. Expiration uses DB time at command; revocation and staleness take effect immediately. Target supersession, hash mismatch, invalid upstream input, withdrawn consent or new blocking issue makes grant STALE. Approval, Decision and Review cannot override deterministic facts, rewrite target content, or stand in for Application commands or ExternalEffect.

## 7. Schema and versioning contract

The physical schema is additive from `0018_current_pointer_same_parent_integrity`. `0019` is reserved for PR2-00 bootstrap/membership and `0020` for PR2-01 source identity if both are authorized. No migration is created here. PostgreSQL 18.x is the integration target. Table names and keys below are normative; `id UUID PRIMARY KEY`, `created_at TIMESTAMPTZ NOT NULL`, actor attribution FK where named, and `ON DELETE RESTRICT` on canonical history FKs apply to every canonical row. Every listed status is persisted UPPER_SNAKE_CASE with a CHECK; terminal/frozen semantic columns are DB protected from UPDATE/DELETE by trigger or equivalent constraint mechanism. Archive updates only the owning identity/operational status and never cascades.

For identity/version pairs, `UNIQUE(parent_id, version_number)`, `UNIQUE(parent_id,id)` on version rows and composite `(identity.id,identity.current_version_id) → version(parent_id,id)` enforce same-parent current pointers. A current pointer is nullable until a FROZEN version exists, and may point only to a FROZEN version under the same identity. Superseding switches the pointer to the newly frozen row in the same transaction that marks the old row SUPERSEDED. Every version has `version_number > 0`, exact parent FK and actor FK. Scientific relations are concrete typed FKs, never `type/id` as the sole formal edge. All relation rows have a unique ordinal within their parent/kind, parent and target lookup indexes, no delete cascade after parent freeze, and a same-project application check plus DB enforcement where both project keys exist.

### 7.1 Exact `0019` contract

`0019_phase2_bootstrap_membership` contains five new tables (the three principal tables below plus two append-only event tables) and their indexes/triggers. The existing Phase 1 `actors` and `projects` columns and constraints remain byte-for-byte unchanged. All UUIDs are Application-supplied; all timestamps are `TIMESTAMPTZ`, provided by the Application clock except lock/expiry checks that use database time.

| Table | Exact columns | Constraints/indexes |
|---|---|---|
| `project_memberships` | `id UUID`, `project_id UUID`, `actor_id UUID`, `status VARCHAR(16)`, `started_at TIMESTAMPTZ`, `ended_at TIMESTAMPTZ NULL`, `created_by UUID`, `created_at TIMESTAMPTZ`, `row_version INTEGER` | PK `id`; FKs project/actor/creator RESTRICT; `UNIQUE(project_id,actor_id,started_at)`; partial unique `(project_id,actor_id) WHERE status='ACTIVE'`; CHECK status in ACTIVE/SUSPENDED/ENDED, row_version>0, ended_at NULL unless ENDED, and ended_at>=started_at when present; indexes `(actor_id,status)`, `(project_id,status)`. Suspension and ending append an immutable membership event row before updating only status/end time. |
| `project_role_assignments` | `id UUID`, `membership_id UUID`, `project_id UUID`, `actor_id UUID`, `role VARCHAR(16)`, `effective_from TIMESTAMPTZ`, `effective_until TIMESTAMPTZ NULL`, `assigned_by UUID`, `created_at TIMESTAMPTZ`, `row_version INTEGER` | PK `id`; membership/actor/project/assigner FKs RESTRICT; composite `(membership_id,project_id,actor_id)` FK to membership unique key; CHECK role in OWNER/RESEARCHER/REVIEWER/APPROVER/VIEWER and `effective_until>effective_from` when present, row_version>0; partial unique `(membership_id,role) WHERE effective_until IS NULL`; index `(project_id,role,effective_until)`. | `bootstrap_records` | `id UUID`, `deployment_id TEXT`, `request_id UUID`, `request_fingerprint CHAR(64)`, `operator_credential_id TEXT`, `secret_digest_id TEXT`, `first_actor_id UUID`, `first_project_id UUID`, `first_membership_id UUID`, `first_role_assignment_id UUID`, `completed_at TIMESTAMPTZ`, `content_hash CHAR(64)`, `hash_scheme VARCHAR(32)` | PK `id`; unique `deployment_id`, unique `request_id`; actor/project/membership/role FKs RESTRICT; CHECK hash strings are 64 lowercase hex, nonblank identifiers, scheme=`sha256-cjson-v1`; UPDATE/DELETE forbidden; indexes on first actor/project. |

Membership has `UNIQUE(id,project_id,actor_id)` to support the composite role FK. A separate `project_membership_events(id,membership_id,prior_status,new_status,actor_id,occurred_at,reason)` and `project_role_events(id,role_assignment_id,actor_id,event_kind,occurred_at,reason)` are append-only support tables in `0019`, with concrete FKs RESTRICT and indexes by parent/time. Their semantic columns and actor attribution are immutable; they have no scientific content hash. This makes temporal changes auditable. The bootstrap record is inserted in the same transaction as the first actor, project, membership and role. Database check/trigger prevents more than one BootstrapRecord and verifies that its role is OWNER for its first membership.

No Phase 2 formal FK uses `ON DELETE CASCADE`. Phase 2 migrations must verify fresh DB→head and frozen `0018`→head on PostgreSQL 18.x. Each migration performs a fail-closed preflight before enforcing new constraints; invalid legacy state stops upgrade without rewriting Phase 1 history. Downgrade is supported only for an empty new canonical table set; otherwise it aborts with an explicit data-preservation error. `0019` must not change any Phase 1 table, constraint, hash, or lifecycle; it adds only membership, role, their event rows and bootstrap tables. `0020` adds only public source identity, identifiers, their verification event table and typed project access links, contingent on the PR2-01 gate. PR2-02 source lineage adds SourceVersion, SourceMergeRecord and MERGED alias fields in its separately reviewed migration. Global source identity never grants cross-project read access; each project needs an explicit link and active actor membership.
