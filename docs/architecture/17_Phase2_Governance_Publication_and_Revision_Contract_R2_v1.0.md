# Phase 2 Governance, Publication and Revision Contract R2 v1.0

**Status:** normative design correction for independent Phase 2 reauthorization review. It authorizes no implementation, migration, external send or later PR.
**Authority:** Final Architecture Correction Addendum A18 admits the R2 corrections and any added schema below. This document overrides only conflicting Phase 2 governance, revision, authorship and prepared-package details in the Phase 2 specification and R1 correction/field contract. The System Architecture, Global Registry, Phase 1 contracts and R2 hash payload contract otherwise remain in force.
**Boundary:** `SubmissionVersion`, `SubmissionRecord`, venue connector, Command-to-ExternalEffect submission chain and actual send are deferred. A `PreparedSubmissionVersion` proves only what was prepared.

## 1. Finite approval policy (P1-07)

The following is the **complete** Phase 2 approval-purpose × target × command policy. The uppercase purpose and command names are persisted values. Every other tuple fails `APPROVAL_PURPOSE_TARGET_COMMAND_INVALID` at request, decision and consumption; a role, OWNER status, P4 label, free-text condition or earlier approval cannot widen the table.

| Purpose | Only request target and state | Required independent review and DecisionRecord | Only consuming Application command and caller | Atomic postcondition |
|---|---|---|---|---|
| `INTERNAL_SCIENTIFIC_RELEASE` | Exact FROZEN, currently valid `ScientificConclusionVersion` | At least one completed `InternalReviewRecord` targeting that exact version/hash; no OPEN blocking issue; `DecisionRecord.decision_type=INTERNAL_SCIENTIFIC_RELEASE` with exact conclusion and review basis | `record_internal_scientific_release`, active RESEARCHER or OWNER | One `ApprovalGrantConsumption.result_scientific_conclusion_version_id` equals the request target. That immutable consumption is the internal release fact; no conclusion material changes. |
| `READY_FOR_SUBMISSION` | Exact FROZEN, currently valid `ManuscriptVersion` belonging to a Publication in `INTERNAL_REVIEW` | At least one completed independent manuscript review targeting exact version/hash; no OPEN blocking issue; `DecisionRecord.decision_type=READY_FOR_SUBMISSION` with exact manuscript and review basis | `transition_publication_ready`, active RESEARCHER or OWNER | Publication moves `INTERNAL_REVIEW→READY`; one lifecycle event cites the decision and grant consumption; consumption's `result_publication_id` is the manuscript's Publication. |
| `PREPARE_SUBMISSION` | Exact FROZEN, currently valid `ManuscriptVersion` belonging to a Publication in `READY` | The same exact manuscript review gate plus a distinct `DecisionRecord.decision_type=PREPARE_SUBMISSION` with manuscript and review basis; `READY_FOR_SUBMISSION` grant alone is insufficient | `freeze_prepared_submission`, active RESEARCHER or OWNER | One same-publication PREPARED package freezes with exact manuscript, authorship and manifest; consumption's `result_prepared_submission_version_id` equals that package. No external effect occurs. |

For all three rows the requester is an authenticated actor with ACTIVE membership and effective RESEARCHER or OWNER assignment in the target Project. The approver is an authenticated **HUMAN** actor with ACTIVE membership and effective APPROVER assignment in that same Project at decision time. The approver differs from requester, the basis DecisionRecord's deciding actor, every target material author/contributor and every required reviewer; each reviewer differs from the target material authors and requester. `acting_on_behalf_of`, Project OWNER, CorrespondingAuthor and an Agent-held APPROVER role do not satisfy the HUMAN approver requirement. A reviewer who also happens to hold APPROVER cannot approve that reviewed request. No self-authored review, decision or request can be laundered through another actor's role. COI/identity checks are against exact actor IDs and effective assignments, under the same transaction as each command.

For each and only each table row, the request command is `request_approval(purpose, exact_target_id, basis_decision_id, review_ids)` by that RESEARCHER/OWNER against the row's target state; it creates PENDING and consumes no grant. The approval command is `decide_approval(request_id, APPROVE|APPROVE_WITH_CONDITIONS|REJECT, typed_conditions)` by the independent HUMAN APPROVER against that same still-PENDING request and revalidated row state; it creates the one immutable ApprovalDecision and, for an approving outcome, one scoped ACTIVE grant. There is no generic request, decision or grant command that accepts an unlisted purpose/target pair. The required `InternalReviewRecord` is created by `record_internal_review` under effective REVIEWER or OWNER role, with the author/requester independence rule above. The required affirmative `DecisionRecord` is created by `record_decision` under effective OWNER or APPROVER role, independent of the target's material authors and with exact frozen review/target basis. A `VIEWER` can read authorized history only. OWNER does not substitute for the independent HUMAN APPROVER at `decide_approval`; one person cannot satisfy mutually independent review, decision and approval checks merely by accumulating roles.

An approval request stores `project_id`, exactly one concrete target FK (`manuscript_version_id` XOR `scientific_conclusion_version_id`), exact `target_content_hash`, `target_hash_scheme`, one listed purpose, `requested_by`, `requested_at`, and PENDING/DECIDED/WITHDRAWN. The Project equals the target parent Project. Its target hash and frozen state are verified on create, decide and consume. For every row, `approval_requests.basis_decision_id` is a **non-null concrete FK** to the required immutable DecisionRecord. The decision has the same Project, matching purpose/decision type, an affirmative decision, and typed basis rows to the exact target and to each required `InternalReviewRecord`; its basis hash is verified. The decision and reviews must predate the request. The request also has typed `approval_request_reviews(request_id,internal_review_record_id)` rows, unique by pair, for the finite set evaluated by the gate. Their review targets must equal the request target ID/hash, and their reviewers must pass independence. These FKs and relation rows are added to the design registry through A18 before implementation; neither a JSON basis nor a generic target locator is allowed. A new blocking issue or a newly invalid scientific input fails the gate even if an older review/decision was favorable.

Request creation and decision each recheck full frozen provenance closure, deterministic validity, target hash, current blocking issues, required reviews, affirmative decision basis, actor independence and project status. `ApprovalDecision` is unique by request and immutable. `REJECT` creates no grant. `APPROVE` or `APPROVE_WITH_CONDITIONS` creates exactly one grant in the decision transaction. Conditions are limited to typed `valid_until` and `requires_current_author_consent`; free text cannot be executable policy. A conditional `requires_current_author_consent` can only strengthen the gate and is mandatory true for `PREPARE_SUBMISSION` at consumption. Approval cannot turn INVALID evidence into a valid scientific fact.

The grant's entire executable scope is the typed tuple `(project_id, purpose, request's concrete target FK, target_content_hash, allowed_command, valid_until, max_uses=1)`. `allowed_command` is the single command in the table; `valid_until` is finite and non-null, later than decision time, and cannot exceed the Phase 2 policy maximum of 30 days after decision. If the immutable ApprovalDecision's `valid_until` is null, the grant expiry is exactly `decision_at + interval '30 days'` in UTC; otherwise the grant expiry equals that decision value after checking it is later than `decision_at` and no later than the same 30-day bound. Its bound is checked against PostgreSQL transaction time at consumption; a caller-supplied clock is never authoritative. No wildcard, grant transfer, target substitution or purpose escalation exists. Grant scope is a projection of concrete columns/relations, not JSON or `target_type + target_id`.

Consume by locking the grant and target in one Application/UoW transaction, checking ACTIVE status, expiry, role validity of the original approver, target ID/hash/current validity, review/decision basis, blocking issues, typed conditions, caller role and exact command. The same transaction performs the postcondition, inserts exactly one immutable `approval_grant_consumptions` row with a unique grant FK and command key, changes grant `ACTIVE→CONSUMED`, and appends a grant event. The result FK XOR matches the table row; database checks and a trigger enforce target/result same-parent where needed. An identical replay of the same command key and normalized arguments returns the recorded result; a changed replay conflicts. A different command key cannot consume an already consumed grant. Failure rolls back all writes. Request, decision, grant, transition, consumption and event are independently queryable with actor, DB time, exact target hash, command key and checked-basis IDs. No approval directly executes a command.

`ApprovalGrant` is `ACTIVE→CONSUMED|EXPIRED|REVOKED|STALE` only; terminal state never returns ACTIVE. Superseded target identity navigation alone does not invalidate an exact frozen target, but a newer target version selected for the same purpose, target/hash mismatch, upstream INVALID/STALE fact, new blocking issue, consent withdrawal, loss of required current author consent, or approver's effective authority loss makes any unused grant STALE. Role/membership termination that removes the issuing HUMAN's APPROVER authority marks all that actor's live grants STALE and appends grant events in the **same transaction** as the role event. Scheduled `effective_until` or membership expiry has the same effective-time rule: at and after DB time `effective_until`, consumption fails `GRANT_STALE` even before an evaluator persists the stale event; the first observing command persists it. A grant consumed earlier remains historical and is never rewritten.

## 2. Rejection, material equivalence and reconsideration (P1-08)

GOV-012 is a command guard, not a UI convention. A rejected request remains DECIDED with its immutable REJECT decision; no grant exists. Phase 2 deliberately uses a conservative, finite **equivalence rule**: every target in the same `(project_id, approval_purpose)` as any prior rejected request is treated as materially equivalent for automatic resubmission, regardless of Publication/Conclusion lineage, UUID, version, content hash or wording. This may require reconsideration for an unrelated target, but it cannot be defeated by cloning a target or changing cosmetic material. Exact target IDs and verified `sha256-cjson-v1` content hashes still bind each request, review, decision and grant; the equivalence rule never substitutes for that frozen provenance check. No derived fingerprint or second scientific hash is created.

After any REJECT in that Project/purpose, a later request requires a **new** `DecisionRecord.decision_type=RECONSIDER_REJECTION` before request creation. Its deciding actor is an independent HUMAN APPROVER who did not issue the cited rejection and is independent of the new target's requester/authors/reviewers. Its typed basis includes the exact prior rejected ApprovalDecision, the new exact frozen target, and fresh independent `InternalReviewRecord` targeting that version/hash. The reconsideration has a nonblank rationale that addresses the rejection and one of two checkable grounds: (a) a completed typed `RevisionAction` to a changed frozen target, whose exact result FK equals the new request target and whose before/after target material/binding payload comparison demonstrates a relevant change rather than only new IDs, version numbers or whitespace; or (b) a new independent ReviewRecord with an exact frozen basis and a reasoned correction of a specific factual or assessment error in the earlier review. Ground (b) allows explicit reconsideration of unchanged target material but never a silent equivalent resubmission. The subsequent ApprovalDecision still requires the independent HUMAN approver checks in §1. A mere favorable reviewer recommendation, different approver, clone or changed request UUID without this DecisionRecord fails `REJECTION_RECONSIDERATION_REQUIRED`.

Each successor `ApprovalRequest` has `prior_rejected_request_id` concrete self-FK and `reconsideration_decision_id` concrete FK. `decision_basis_approval_decisions(decision_id,approval_decision_id,ordinal)` binds the exact rejection into the DecisionRecord basis hash; `decision_basis_revision_actions(decision_id,revision_action_id,ordinal)` binds ground (a) when used. A RevisionAction cited by a reconsideration DecisionRecord must already be immutable and must not refer back to that DecisionRecord or to any later decision whose basis transitively contains it; the Application and a deferred typed-graph constraint trigger reject this hash/provenance cycle. Ground (b) uses the existing typed `decision_basis_reviews` relation for both the corrected prior review and fresh review, with the DecisionRecord rationale identifying the corrected error. These relations and request columns require A18 Registry/ADR admission before implementation. The prior request must be REJECTED with the same Project/purpose, and the reconsideration DecisionRecord must be unique to this successor request. The Application finds **all** earlier rejected requests in the Project/purpose under a serializable transaction, locks the relevant approval-request scope, and requires the new reconsideration to cite each earlier rejection through typed basis rows; a partial chain or concurrent rejection fails and retries from a fresh read. Audit output includes every cited rejection Request/Decision ID and hash, old/new target IDs and hashes, exact review and RevisionAction basis where applicable, actors, reason and final outcome. Nothing deletes or rewrites rejected history.

## 3. Prepared package and authorship closure (P1-09)

`PreparedSubmissionVersion` is a Publication-owned PREPARED draft then FROZEN immutable snapshot. The package's `publication_id`, `manuscript_version_id` and `authorship_snapshot_id` must all belong to **the same Publication**. `manuscript_versions` and `authorship_snapshots` expose unique `(publication_id,id)` keys; package columns use composite `(publication_id,manuscript_version_id)` and `(publication_id,authorship_snapshot_id)` FKs. `ContributionRecord` has the package's Publication FK, and `authorship_snapshot_contributions` uses a composite `(publication_id,contribution_record_id)` path, with a same-publication constraint trigger where a direct composite FK cannot span the relation owner. An author list member, contribution actor and consent actor are exact Actor FKs. No generic formal reference or `ON DELETE CASCADE` is allowed.

The AuthorshipSnapshot is immutable before package freeze. Each listed author has at least one exact same-publication ContributionRecord in the snapshot relation set **whose `actor_id` equals that author's Actor ID**; a same-publication/actor constraint trigger verifies the match. Every contribution points to a valid actor and has a nonblank role/statement. Corresponding authors are a subset of the ordered author set, and author ordinals are unique and gap-free. The snapshot hash covers its ordered author/contribution relations as specified in the R2 hash contract. It establishes attribution only, never approval authority. Agent contributions may be recorded but do not silently enter the HUMAN author list.

An `AuthorConsent` belongs to exactly one package, originally created PREPARED, and one author Actor; withdrawal remains possible after package freeze. Phase 2 `consent_scope` has the single executable value `PREPARED_PACKAGE`; it acknowledges that exact manuscript/authorship/package preparation, not venue sending. A GRANTED consent requires authenticated HUMAN author identity or a separately recorded legally valid representative authority (the latter is deferred, so Phase 2 accepts only direct HUMAN consent). Consent evidence is a frozen ArtifactVersion and is required for GRANTED and WITHDRAWN rows; no approval role may substitute for an author's own consent. A WITHDRAWN row cites the prior GRANTED or regranted consent through `prior_consent_id`; regrant after withdrawal appends a new GRANTED row citing the withdrawal. Each chain has one root and at most one successor per row, all `(prepared_submission_version_id,actor_id,consent_scope)` equal. A package/author/scope unique root constraint and unique `prior_consent_id WHERE NOT NULL`, plus a same-chain DB trigger, prevent forks and cycles. Current consent is the single terminal head, computed from the immutable chain; GRANTED is current only when that head is GRANTED. No historical consent is overwritten or erased.

Consent append, withdrawal/regrant, grant consumption and package freeze all lock the same package row and use one transaction each. Freeze additionally locks every author chain in sorted Actor-ID order, rereads its head and evidence hash, requires exactly one current GRANTED `PREPARED_PACKAGE` consent per author and no extra unlisted author consent, and stores those exact consent FKs as `AUTHOR_CONSENT` manifest items. The package manifest has concrete category-XOR FKs to ArtifactVersion, SourceVersion, ClaimVersion, ScientificConclusionVersion or AuthorConsent, unique `(package_id,category,ordinal)`, and each consent item uses the same package and one distinct snapshot author. Composite `(package_id,author_consent_id)` FK via a unique key plus trigger enforces same-package and current-head status at freeze; manuscript placements and package item sets must agree on exact claims, conclusions, citations and figure/table artifacts. The manuscript, authorship, manifest targets, consents and their frozen hashes all verify in the freeze transaction. Only the consumed `PREPARE_SUBMISSION` grant for that manuscript may authorize PREPARED→FROZEN. Hashes remain SQL NULL until successful freeze and are sealed with `frozen_at`; later SUPERSEDED/WITHDRAWN retains the frozen bytes and hash.

Withdrawal racing with freeze is serialized on the package lock. If withdrawal commits first, freeze fails until a valid regrant; if freeze commits first, the withdrawal appends history and immediately marks the frozen package's **derived current validity** STALE. It also makes any unconsumed related PREPARE_SUBMISSION grant STALE with an event in the same withdrawal transaction. Regrant does not reactivate a terminal grant or make an already frozen package current again, because its manifest still binds the withdrawn consent record; a new prepared package, current consent and new approval are required. A PREPARED package can accept a regrant on the same chain before freeze. Neither consent nor package state records an external send.

## 4. Completed RevisionAction results (P1-10)

`RevisionAction` records a completed change, never a plan or reviewer suggestion. Every row has `review_issue_id` or `decision_record_id` (or both), immutable actor/time/hash, optional superseding action FK, and the exact typed result below. Its issue and decision refer to the same Project and a relevant exact target/basis. The result must be created/frozen or completed before the action is inserted. An action with no applicable result is `NO_CHANGE` only, with a nonblank rationale in its DecisionRecord. A newer action supersedes the old row and preserves both histories.

| `action_type` | Required concrete result columns (all other result columns NULL) | Completion guard |
|---|---|---|
| `NEW_EXPERIMENT` | `result_experiment_spec_version_id` **and** `result_run_id` | Exact FROZEN ExperimentSpecVersion; Run references that version, has sealed inputs and a terminal SUCCEEDED/FAILED/CANCELLED state. A failed run is still a recorded result, never claimed as positive evidence. |
| `ANALYSIS_CHANGE` | `result_statistical_result_id` | Immutable StatisticalResult with exact Phase 1 measurement/run provenance. |
| `CLAIM_CHANGE` | `result_claim_version_id` | Exact FROZEN ClaimVersion; its evidence set and Phase 1 closure verify. |
| `CONCLUSION_CHANGE` | `result_scientific_conclusion_version_id` | Exact FROZEN conclusion with R2 input closure. |
| `MANUSCRIPT_CHANGE` | `result_manuscript_version_id` | Exact FROZEN ManuscriptVersion with placement closure. |
| `SOURCE_CHANGE` | `result_source_version_id` | Exact FROZEN SourceVersion with correction/lineage basis when required. |
| `NO_CHANGE` | none | Basis DecisionRecord explicitly accepts the issue without material change and gives a nonblank rationale; it cannot mark a blocking issue ADDRESSED by pretending an edit occurred. |

The listed fields replace the R1 four-result XOR. PostgreSQL enforces the finite action CHECK, required-pair rule for NEW_EXPERIMENT, all-other-null checks, exact result FKs and RESTRICT; immutable-row and same-project/frozen-result triggers complete the guard. `NEW_EXPERIMENT` produces two formal edges, so the R2 hash contract's RevisionAction payload must bind both the ExperimentSpecVersion and Run, and `ANALYSIS_CHANGE` must bind StatisticalResult; it cannot keep the R1 single `resulting_version` union. A18 registers these columns and the amended literal hash material before any implementation. `RevisionAction` does not mutate a ReviewIssue to ADDRESSED by itself: the separate issue transition checks the action, exact result and independent reviewer, then appends its own IssueEvent.

## 5. Verification and stop conditions

The later authorized governance PR must use PostgreSQL 18.x to test every allowed tuple and reject the remaining target/state/command cross product; HUMAN/role/independence and reviewer/decision basis; wrong-project/missing concrete FK; immutable review/decision/rejection history; one grant consumption under concurrent commands; expiry, scheduled and immediate role loss, new blocking issues, target invalidity and consent withdrawal. Publication tests must prove same-publication composite FKs, every author contribution and current consent, withdrawal/freeze races, stale projection after frozen withdrawal, hash/manifest closure, and no SubmissionVersion/ExternalEffect creation. Revision tests must cover all seven action types, every wrong result combination and frozen/terminal provenance. Failure paths leave no partial transition, event or consumption. Exact command, database version, migration/constraint evidence and findings go in the authorized PR evidence pack; `not run` is never PASS.

No R2 design correction authorizes implementation. A18 must register the added concrete approval/rejection basis relations, same-publication composite FKs and RevisionAction result fields, amend the hash contract, and pass independent architecture review before a PR may implement them. The Phase 2 PR sequence and Phase 1 freeze remain unchanged.
