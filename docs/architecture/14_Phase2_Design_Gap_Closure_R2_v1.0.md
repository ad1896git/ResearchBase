## 1. Four distinct scientific facts

| Fact | Canonical owner | Material and formal consumer |
|---|---|---|
| Phase 1 Claim support | `research`/`evidence`; frozen `ClaimVersion` and Phase 1 `EvidenceRelation` | The unchanged Phase 1 `support_set_hash` covers only Measurement/StatisticalResult evidence relations. The unchanged Phase 1 Claim `content_hash` includes that hash. The Phase 1 closure verifier remains the sole validator for this fact. |
| Phase 2 literature support for an existing scientific target | `literature`; `LiteratureSupportSnapshot` and `LiteratureEvidenceRelation` | A separate immutable snapshot binds verified LiteratureEvidence to one exact frozen ClaimVersion, ResearchQuestionVersion or HypothesisVersion. Its own Phase 2 binding/content hashes are never written into the target or its Phase 1 support hash. |
| ScientificConclusion support | `research`; `scientific_conclusion_claim_inputs` and `scientific_conclusion_literature_inputs` | One exact frozen input set belongs to each ConclusionVersion. A claim input may additionally bind one exact matching Phase 2 literature support snapshot; direct literature inputs are owned only by the Conclusion input table. The Conclusion's own `support_set_hash` binds these rows. |
| Publication citation placement | `publication`; `ManuscriptCitationPlacement` | Exact SourceVersion placement in an exact ManuscriptVersion. Citation does not assert support and cannot substitute for any of the three scientific support paths. `CitationRelation` remains a derived shorthand, not a table. |

`ClaimVersion` remains an individual scientific assertion. `ScientificConclusionVersion` remains a versioned synthesis over exact frozen scientific inputs. No manuscript prose, provider output, search result or citation placement promotes itself into either fact.

## 2. Literature support schema and ownership

This section replaces R1 correction §2's LiteratureEvidenceRelation row, R1 schema-field contract's `literature_evidence_relations` row, and any older Phase 2 wording requiring a literature relation to enter a Phase 1 target support binding or to be sealed by the target's freeze. It does **not** replace any Phase 1 table or command. ADR-0009 records the schema admission rationale.

`literature_support_snapshots` is the sole Phase 2 aggregate owner of a target's literature support set. It has `id UUID PK`, `project_id UUID NOT NULL` FK to Project, exactly one of `claim_version_id`, `research_question_version_id`, `hypothesis_version_id` nonnull with concrete FK and XOR CHECK, `snapshot_number INTEGER NOT NULL CHECK > 0`, `previous_snapshot_id UUID NULL` self-FK, `literature_support_set_hash CHAR(64) NOT NULL`, `content_hash CHAR(64) NOT NULL`, `hash_scheme VARCHAR(32) NOT NULL CHECK = 'sha256-cjson-v1'`, `created_by UUID NOT NULL` Actor FK, `created_at TIMESTAMPTZ NOT NULL`, and `frozen_at TIMESTAMPTZ NOT NULL`. The referenced scientific version must already be frozen. The target's owning Project must equal snapshot `project_id`, checked by Application and a database constraint trigger traversing the concrete target parent FK. Partial unique indexes on `(claim_version_id,snapshot_number)`, `(research_question_version_id,snapshot_number)` and `(hypothesis_version_id,snapshot_number)` apply to the nonnull target kind. The first snapshot has number 1 and null predecessor; every later snapshot has number previous+1 and an exact predecessor for the same target and Project. A database constraint trigger enforces predecessor target/project equality and consecutive numbering. Concurrent creation locks the target identity and uses SERIALIZABLE transaction isolation; a loser retries from a fresh read or returns `CONCURRENT_MODIFICATION`. There is no mutable latest pointer and no generic target locator. Current navigation selects the highest `snapshot_number` for that exact target. Formal provenance always stores a snapshot ID and hash, never this navigation rule.

`literature_evidence_relations` has `id UUID PK`, `literature_support_snapshot_id UUID NOT NULL` FK RESTRICT, `literature_evidence_id UUID NOT NULL` FK RESTRICT, `relation_type VARCHAR(16) NOT NULL` CHECK in `SUPPORTS, CONTRADICTS, QUALIFIES, MOTIVATES, PRIOR_ART, CONTEXTUALIZES`, `ordinal INTEGER NOT NULL CHECK >= 0`, `qualification TEXT NULL`, `created_by UUID NOT NULL` Actor FK, and `created_at TIMESTAMPTZ NOT NULL`. It has UNIQUE `(literature_support_snapshot_id,ordinal)` and `(literature_support_snapshot_id,literature_evidence_id,relation_type)`, indexes on evidence and snapshot, and no own scientific content hash. The relation targets its scientific version through its snapshot, so there is only one owner path. Its application and database guards require the evidence and snapshot projects to match, the evidence content hash to verify, and its SourceVersion to be frozen. A `SUPPORTS` relation additionally requires current evidence state VERIFIED and a non-retracted SourceVersion at creation. Contradiction/qualification remains typed and cannot count as positive support. A target with no current literature support may have an explicit empty new snapshot; absence of any snapshot means no Phase 2 literature support has been asserted. Each snapshot and its relation set are immutable after the transaction commits; no UPDATE/DELETE and no `ON DELETE CASCADE`.

An Application `create_literature_support_snapshot` command creates the numbered snapshot and complete relation set in one SERIALIZABLE PostgreSQL transaction. It first validates authenticated active membership and effective RESEARCHER/OWNER role; exact target Project and frozen Phase 1 material; Phase 1 closure for a Claim; verified evidence and frozen SourceVersion; current deterministic validity; relation cardinality/uniqueness; and predecessor. For every positive `SUPPORTS` edge, the evidence's latest verification event must be `VERIFIED` by an authenticated HUMAN reviewer distinct from the extraction actor and support-snapshot author. Agent/Skill extraction or assertion alone cannot enter canonical positive support. The same independent-human verification rule applies to direct positive ScientificConclusion literature inputs. It computes the Phase 2 binding and own hash from the literal R2 hash contract, inserts all rows, then seals them at commit. Deferred database constraint triggers verify relation cardinality, same-parent identity, frozen target/evidence state, digest format and immutable seal; they do not attempt a second SQL implementation of `canonical-json-v1`. The Application recomputes both digests and full closure before commit, and every formal provenance read independently recomputes and compares the digests and closure. Failed validation rolls the entire command back. The command never calls `freeze_claim_version`, edits `ClaimVersion`, or edits Phase 1 `EvidenceRelation`.

Every formal read of a literature support snapshot recomputes its binding/content hash from its immutable relation rows, verifies exact target/evidence frozen hashes, and runs the unchanged Phase 1 closure verifier for a Claim target. An invalid or retracted SourceVersion, disputed/rejected Evidence, invalid Claim or a newer correction marks the snapshot's **derived current validity** STALE/INVALID and propagates to dependent ConclusionVersion and ManuscriptVersion queries. Historical snapshot bytes and old Claim bytes stay unchanged. A corrected support set creates a new snapshot; old conclusion versions keep their exact old snapshot reference and show current invalidity as a projection.

The canonical hash owner is `LiteratureSupportSnapshot`: `literature_support_set_hash` binds the complete ordered relation list, and `content_hash` binds project, exact target reference, predecessor reference and binding hash. The complete literal material, null rules and golden vector belong to the R2 hash contract. The relation has no second hash or independent current pointer. R1's direct literature support relation to DRAFT Claim/Question/Hypothesis, sealed by that target's freeze, is explicitly superseded.

## 3. ScientificConclusion closure

`ScientificConclusionVersion` remains DRAFT until its own Application freeze. `scientific_conclusion_claim_inputs` has exact `claim_version_id`, `relation_type`, `ordinal`, and nullable `literature_support_snapshot_id`. The snapshot, if present, MUST target the same `claim_version_id` and Project; a composite FK through a unique `(snapshot.id,snapshot.claim_version_id)` key plus a freeze equality guard enforces this. The snapshot is immutable and hash-verified. `scientific_conclusion_literature_inputs` has exact `literature_evidence_id`, relation type and ordinal. These tables are the only owner of a Conclusion input fact; they do not copy `literature_evidence_relations` rows. A direct LiteratureEvidence input and a snapshot binding to the same Evidence within the same Conclusion are rejected as duplicate positive support unless one relation is explicitly CONTRADICTS/QUALIFIES and the statement/limitations acknowledge that difference.

Freeze requires at least one input, exact frozen Phase 1 Claim validation, exact verified literature support snapshot when bound, exact verified direct LiteratureEvidence for positive support, non-retracted SourceVersion at freeze, unique typed ordinals, and no unresolved latest/current navigation. It computes the literal `support_set_hash` then `content_hash` in one transaction and seals rows. DRAFT may add/remove inputs. A later input change creates a new ConclusionVersion. Supersession changes only its own same-parent current pointer; downstream ManuscriptClaimPlacement stores the exact frozen ConclusionVersion. Upstream retraction/dispute/invalidity yields a derived STALE/INVALID projection; no old hash is rewritten. `INCONCLUSIVE` and `MIXED` remain valid typed judgments when support, contradiction and limitations are represented accurately.

## 4. R2 precedence and phase sequence

Addendum A18 is the sole mechanism granting these R2 corrections precedence over conflicting Phase 2 R1 wording. The Global Registry's naming/ownership remains authoritative except for the explicit `LiteratureSupportSnapshot` admission and relation ownership correction above and the precise R2 field changes in companions 15–17. The R2 hash contract supersedes R1 correction §4 and field contract's conflicting hash and ordering rules. The R2 identity contract supersedes R1 bootstrap, OWNER and PR2-01 source workflow details where they conflict. The R2 governance contract supersedes R1 approval, revision, authorship and package fields where they conflict. Unmentioned System Architecture and Phase 1 contracts remain in force. No new Phase 1 content material, support hash, closure rule, provenance meaning or version lifecycle is authorized.

The R1 schema-field contract requested a `project/status` index on `literature_search_plans`, but that identity table has no `status` column. R2 removes that invalid index requirement. The plan identity table instead has an index on `(project_id,current_version_id)`; lifecycle status is persisted only on `literature_search_plan_versions`, with an index on `(plan_id,status)`. No derived identity status is added or hashed.

Migration sequence remains `0018` frozen Phase 1 → `0019` PR2-00 → `0020` PR2-01, each only after its own authorization. The support snapshot pattern is **not** placed in either PR2-00 or PR2-01; a later LiteratureEvidence/support PR must receive separate migration authorization. No Phase 2 implementation, migration or provider activation is authorized by this design correction.
