# HG1-02 local Human review integration

The foreground HG1-01 Runner keeps version 1 `whoami` and `project.get`. Version 2 adds only `enrollment.challenge`, `enrollment.prove`, `enrollment.attest`, `enrollment.provision`, `reviewer.assign`, `source.inspect`, `evidence.get`, `evidence.review`, and `support.create`. Requests are exact-key JSON frames of at most 4096 bytes. One request is accepted per Unix connection. The Runner reads the peer UID with macOS `getpeereid`; no request may provide an actor, principal, role, credential, deployment, or operator identity as authority.

HG1-02 is disabled until the trusted host administrator installs a root-owned, non-user-writable `/Library/Application Support/ResearchBase/hg1-02-{final|live|live2|live3}.json`. Its exact schema is `version`, `deployment_id`, `operator_uid`, `operator_public_key`, `operator_public_key_sha256`, `audit_root`, and three `peers` records (A, B, C), each with `uid`, `actor_id`, `credential_id`, `not_before`, and `not_after`. The file and every parent must be root-owned and not writable by group or others. The existing onephone installation must match A's actor, credential, and deployment. The audit root is a private directory directly under `/Users/onephone/ResearchBaseData/migration-evidence`. A policy change or removal fails credential validation on the next request and at Application credential rechecks. No HG1-02 host policy or real B/C credential is installed by this implementation.

B first obtains and answers a fresh random challenge through B's own kernel-authenticated socket. The Runner records a digest binding the challenge, nonce, B's trusted UID/credential, deployment, and preselected actor UUID. C independently signs a bounded, secret-free provisioning record with C's Ed25519 private key outside the Runner. The protected content-addressed audit file contains the signed material, evidence source, UTC signing time, and B's live-proof digest. The Runner checks the file's path, owner, mode, SHA-256, pinned C public key, signature, deployment, all identities, freshness, and exact live-proof digest. C must submit that record from C's own kernel-authenticated socket. A then invokes the existing `Phase2IdentityService.provision_actor` and `assign_project_role` as the canonical OWNER. No proof, actor, binding, membership, role, event, or scientific row is synthesized by the Runner. Duplicate subject and replay protection remain in the Application transaction; the in-memory challenge is single-use and expires with the short-lived Runner.

For M3, the Runner derives B's current principal from the canonical active HUMAN binding and a live deployment credential. `source.inspect`/`evidence.get` delegate to `LiteratureEvidenceService` reads; B-only `evidence.review` fixes status to `VERIFIED`; A-only `support.create` fixes the relation to one `SUPPORTS` edge. The existing Application service checks active project membership, effective role, credential, binding, temporal authority, extractor/reviewer/snapshot-author separation, frozen target, source/CAS integrity, and durable request replay. No scientific hash algorithm, schema, migration, PostgreSQL HBA, or retained M2 state changes.

The root-controlled policy and independent C/B host accounts are operational prerequisites for a real ceremony. Technical tests use disposable PostgreSQL/CAS and synthetic test identities. They do not claim witnessed Human B verification. A distinct-UID Runner host test remains `NOT_RUN` when noninteractive sudo access is unavailable.
