# PR3-16 actor-only lock composition

This is a reviewable Q7 composition for the six search commands, before S2. It does not freeze the contract or authorize implementation. The owner requires explicit per-caller composition and does not authorize copying the gateway helper (`docs/phase3/PR3-16-owner-decisions-2026-10-27.md:13`). Statuses below distinguish source-established requirements from the remaining selection and absent checks.

## Per-caller trace

**RESOLVED — common prefix.** Human and Agent commands each use one synchronous READ COMMITTED task transaction. First Application SQL is exactly the sorted 18-table SHARE in `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:215` through `:226`; no preliminary authentication or receipt SELECT, SET LOCAL, advisory lock, write or autoflush. Then acquire `rb_phase2_lock_project(project_id)`, `pr301:command:<project_uuid>:<authenticated_actor_uuid>:<command_uuid>`, and `pr301:task:<task_uuid>`, in that order. Invoke fresh validation after each blocking stage, including the SHARE. Sources: `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:229`, `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:247`, `src/researchbase/persistence/task_safety_repository.py:55`.

**OWNER — identity slot, before any row lock.** For a verified Human caller, the proposed trace has no PR3-02 identity advisory key. For a verified Agent caller, the proposed trace takes `pr302:actor:<authenticated_actor_uuid>` and invokes fresh validation immediately afterward; it takes no version or execution key. Both then continue to the common rows below. Question: does architecture review approve this actor-only key selection and the absence of an actor row lock for each caller? Options: (1) approve this proposed Human/Agent split; (2) specify a different existing identity coordination and its position before task rows, with mixed-writer evidence. Recommendation: option 1 for review, not an established freeze: the actor key exists in the version writer (`src/researchbase/persistence/agent_version_repository.py:77`); that writer also locks actor rows (`src/researchbase/persistence/agent_version_repository.py:81`), so it does not itself establish the search recipe. The owner answer requires current verified actor-only planning, no AgentVersion or availability prerequisite, and required identity keys before rows, but leaves the exact composition open (`docs/phase3/PR3-16-execution-pack-r2.md:47`, `docs/phase3/PR3-16-execution-pack-r2.md:56`, `docs/phase3/PR3-16-execution-pack-r2.md:521`). No key may be appended after row locks.

**RESOLVED — common rows and reads.** After the identity slot, lock `research_tasks` FOR UPDATE, then `research_task_steps` FOR UPDATE in ascending ID; read dependencies by predecessor/dependent and task and step inputs by ID. Read safety tables in this order, ascending ID within each: `budget_reservations`, `budget_usage_records`, `checkpoint_policies`, `checkpoint_policy_dataset_scopes`, `checkpoint_policy_metric_scopes`, `execution_budgets`, `human_checkpoints`, `termination_policies`. Read lineage events, node_runs, nodes, sessions in table-name/ID order, then exact scientific versions and Runs. Do not lock immutable lineage or Run rows, or implicitly lock checkpoints. Sources: `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:235`, `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:238`, `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:243`, `docs/phase3/PR3-16-execution-pack-r2.md:168`. The existing `lock_safety` locks checkpoints, so it is not this read recipe (`src/researchbase/persistence/task_safety_repository.py:86`).

**RESOLVED — validation and effects.** After every wait, including row, FK and constraint waits, authenticate and check current read entitlement, then inspect the committed project/actor/command receipt. Equal hash returns original IDs before write authority, state or CAS; unequal hash conflicts. With no committed receipt, refresh write authority and all applicable admission predicates before effects. After each DML and constraint forcing, refresh entitlement, committed replay and fresh admission; exclude this transaction's own uncommitted receipt from replay. Update the task once, insert the declared receipt, lineage and task event/result effects, force deferred constraints while holding locks, then commit once; failure rolls back. Sources: `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:137`, `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:247`, `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:251`, `docs/phase3/PR3-16-execution-pack-r2.md:56`, `docs/phase3/PR3-16-execution-pack-r2.md:292`.

**OWNER — callback implementation.** Question: what exact callback interface and committed-receipt visibility mechanism will distinguish an original committed receipt from this transaction's own effects after each DML and constraint check? Options: (1) specify and review that mechanism with the receipt/guard design; (2) defer S2 until it is specified. Recommendation: option 1, without treating the existing optional `after_wait` callback as a complete post-write contract (`src/researchbase/persistence/task_safety_repository.py:55`, `docs/phase3/PR3-16-freeze-inventory.md:293`). The observable order above remains mandatory.

**RESOLVED — boundaries.** No AgentVersion lookup, version/availability lock or availability admission prerequisite follows from actor-only planning; preserve Agent attribution and disabled execution. No new advisory namespace, task-table SHARE, lock upgrade or trigger-acquired advisory lock. Only 40001/40P01 permit up to three fresh whole attempts; timeouts do not automatically retry. Formal reads use one lock-free REPEATABLE READ READ ONLY snapshot. Sources: `docs/phase3/PR3-16-execution-pack-r2.md:47`, `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:255`, `docs/proposals/PR3-16_Search_Lineage_Contract_DRAFT.md:261`.
